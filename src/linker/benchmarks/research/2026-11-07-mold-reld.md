# Performance research: mold and reld — 2026-11-07

The active optimization track is **single-threaded**, per the user's subsequent
direction: profile full links, reduce allocation and repeated work, and consider
compact IDs. Parallel parsing and other parallel passes are deferred. Keep the
1.0 compatibility contract and failure-preserving publication. The follow-up
[small serial investigation](2026-11-07-serial-probe.md) measures the release
before selecting an implementation change.

This is a source review and implementation proposal, **not a new benchmark**.
Neither competitor was built or timed. No linker implementation or dependency
changes accompany this report. The November 5 measurements below predate 1.0;
they identify experiments, not current release timings or promised speedups.

## What their code does, and what transfers

| Area | mold | reld native ELF | Fas implication |
| --- | --- | --- | --- |
| Work scheduling | Rayon work within passes; worker-local results; explicit joins | Parallel input work, symbol groups and bucket processing | Use coarse batches and barriers; keep the inexpensive path serial |
| Symbol identity | Dense `SymbolId(u32)`; names gathered into 64 independently owned hash shards | Dense symbol IDs, flat definition/flag/file-ID vectors, prehashed names | Resolve names once; let relocation passes use IDs and arrays |
| Input bytes | Read small regular files; map larger files; archive members are slices | Mapped inputs and borrowed archive ranges | Try bounded slices over existing strings before changing the I/O backend |
| Archive work | Discover/parse member metadata up front and later decide live files | Process member inputs in parallel, collect results in member order, then select entries | Preserve our lazy extraction and GNU selection rules while making their representation cheaper |
| Output work | Assign owned byte ranges, then copy/relocate in parallel | Layout allocates output parts; independent writers fill them | Fix layout and ownership first; parallel writes come afterwards |
| System costs | Output mapping/preallocation, optional block reuse and fork-based exit-latency hiding | Output creation can overlap other work; mapping/buffering and replacement policies are explicit | Separate algorithm cost, file I/O, caller latency and process cleanup in measurements |

### Partition work instead of sharing one mutable table

mold's current symbol interning is **two-phase batched sharding**, not a single
lock-free global symbol map. Parsing records names and their destination slots
into hash bins. Each gather task owns one shard, hashes are reused, and IDs are
written back to the recorded slots. Its separate `ConcurrentMap` is used for
mergeable data; do not confuse that with the symbol table.
Sources: [symbol gathering](https://github.com/rui314/mold/blob/331ac663668dc0b1f4949403854613b9b1913025/elf/symbol.rs#L1462),
[merge-data map](https://github.com/rui314/mold/blob/331ac663668dc0b1f4949403854613b9b1913025/common/concurrent_map.rs).

reld similarly reads symbols by file groups, queues prehashed names by bucket,
then populates different buckets independently. Its definition and flag arrays
are split into owned ranges during loading. Group size depends on symbol counts
and available workers; a single-thread configuration avoids unnecessary grouping.
This is a useful model for OCaml Domains: worker-local construction, immutable
inputs, an ordered join, and one owner for each mutable shard. We do not need
a new lock-free table as the first step.
Sources: [symbol database](https://github.com/forge-ci/reld/blob/6ab41368d686c7c2eec570182dd11d7d6ddf1efe/crates/reld-core/src/symbol_db.rs#L1627),
[group sizing](https://github.com/forge-ci/reld/blob/6ab41368d686c7c2eec570182dd11d7d6ddf1efe/crates/reld-core/src/grouping.rs#L248).

For Fas, a first ID conversion can leave the ordered resolver intact. Once it
has selected definitions, build per-input canonical-reference arrays. Later
GOT/TLS/relocation work can use those arrays rather than repeatedly translating
names and version keys. Preserve separate local-symbol identity, symbol versions,
visibility, weak-undefined behavior, COMDAT decisions and dynamic preemption.

### Remove copies before adopting mmap everywhere

mold's mapped-file implementation uses a 32 KiB read threshold at this revision.
Its comments explain the tradeoff: many tiny mappings contend on address-space
management; copying large files consumes memory bandwidth. This is a measured
choice for its workloads and allocator, not a threshold to transplant into OCaml.
Source: [input storage](https://github.com/rui314/mold/blob/331ac663668dc0b1f4949403854613b9b1913025/common/mapped_file.rs#L88).

Fas already caches repeated positional-input bytes within one invocation.
However, `Archive.object_` copies a selected member with `String.sub`, and
`Binary.string_at` copies each decoded name. Prototype a bounded input view
`(backing bytes, base, length)` and compact archive-index/name storage first.
Keep separate per-occurrence extraction state: repeated archives must not share
their mutable `loaded` flags or parsed objects that later passes modify.

A view must check its own bounds, not merely the containing archive's bounds.
Retain existing byte/name budgets, truncated-file diagnostics, advertised-export
validation, thin/nested archive handling and malformed-unused-member policy.
An mmap experiment should be separate: mapping changes the input-mutation and
truncation failure model, and may increase measured RSS through mapped pages.

### Parallel parsing must not change resolution

mold reads independent inputs concurrently, records command-line positions and
restores order afterwards. Script effects are handled explicitly; its reader
even documents which future script directives would invalidate deferred parsing.
Source: [parallel reader](https://github.com/rui314/mold/blob/331ac663668dc0b1f4949403854613b9b1913025/elf/reader.rs#L292).

Fas currently expands scripts/search paths and prepares inputs sequentially.
That boundary can produce ordered work descriptors; workers can parse independent
ordinary objects into slots, and the resolver can consume those slots in order.
Keep diagnostics and aggregate resource-budget checks deterministic too. Do not
let scheduling choose a weak definition or COMDAT winner.

In particular, **do not transplant mold's archive-resolution algorithm**. Its
live-file walk is deliberately less dependent on archive command-line order.
Fas's `Resolver.extract` uses indexed pending/deferred member sets to implement
GNU forward passes; a newly needed earlier member waits until the next pass.
Preserving those rules is part of our existing contract, not redundant scanning
that can simply be removed. Parallelize discovery or selected-member parsing
only where the selected set and ordered commit remain well-defined.
Sources: [mold resolution](https://github.com/rui314/mold/blob/331ac663668dc0b1f4949403854613b9b1913025/elf/passes.rs#L661),
[mold paper, §4.2](https://arxiv.org/html/2608.23228v1#S4.SS2),
[Fas resolver](../../resolver.ml).

### Compact storage and output ownership matter in OCaml

Fas's symbol/relocation arrays hold individual records, copied name strings and
boxed 64-bit values. An array of record pointers is not equivalent to a packed
native array. Test flat integer arrays for bounded IDs/offsets and packed bytes
or another unboxed representation for full-width addends. Profile the access
cost as well as allocation. ELF arithmetic still requires full 64-bit bit
patterns; OCaml's immediate integer range cannot replace every `int64` safely.

The first parallel emission experiment should own complete output ranges after
layout, symbol values and synthetic-section plans are frozen. Special writers
for unwind data, merged sections, dynamic tables and build IDs must have explicit
dependencies. A task per relocation is too fine-grained. mold explicitly groups
chunks that touch one another's ranges; reld splits very large copies into enough
chunks to balance workers without creating thousands of tiny tasks.
Sources: [mold output ownership](https://github.com/rui314/mold/blob/331ac663668dc0b1f4949403854613b9b1913025/elf/driver.rs#L652),
[reld copy policy](https://github.com/forge-ci/reld/blob/6ab41368d686c7c2eec570182dd11d7d6ddf1efe/crates/reld-core/src/file_writer.rs#L35).

Fas's embedded entry point returns `bytes`; file publication is a separate
temporary-file/rename operation. Keep that API and its failure guarantees.
Writing straight into the old output, deleting it early, leaking invocation
state until process exit, or returning while a child is still finishing work
would change those guarantees. If output copying becomes a proven bottleneck,
investigate a private temporary mapped output behind the file API separately.
Do not assume these OS-level changes explain the current performance gap.

## What our existing evidence actually says

The [November 5 baseline](../README.md) shows warm-cache Fas/LLD time ratios of
1.46–3.45 on seven applications, and approximately 6 on the 1,024-needed-member
synthetic archive. One-of-1,024 archive extraction still spends about 46 ms in
the aggregate parse phase despite selecting one member. This points first at
index/name representation and parsing work, not just relocation application.
It does not prove the same bottleneck exists on the released source.

The old static Chibicc statistics also show substantial parse and emission
allocation; final writing is much smaller in that sample. `resolve` includes
member parsing and `emit` includes relocation, so their counters overlap.
Do not add phase totals or interpret sampled allocation shares as CPU shares.
The prior SHA-1/IFUNC improvements are already implemented, so they are not
new optimization candidates. Reprofile 1.0 before ranking the remaining work.

There is no defensible percentage of the slowdown attributable to OCaml yet.
The code review identifies language-sensitive allocation costs and independently
fixable algorithm/data-layout costs. Multicore scaling is another separate
factor. The mold paper reports near single-thread parity with LLD on one large
workload and much larger gains at higher thread counts; that supports measuring
both dimensions, not predicting a universal multiplier for our machine.
Source: [mold paper, §7.3](https://arxiv.org/html/2608.23228v1#S7.SS3).

## Proposed implementation order and acceptance

| Step | Deliverable | Evidence needed before keeping it |
| --- | --- | --- |
| P0: released baseline | Capture exact 1.0 binary, current compiler/tool versions, qualified input closures and per-pass CPU/allocation profiles | Verified outputs, raw samples and a profile that identifies the first target |
| P1: archive and input representation | Bounded member views and cheaper index/name storage, one change at a time | Same extraction/diagnostic behavior; lower allocations and repeatable gains on lazy and all-member archives plus real programs |
| P2: canonical IDs and compact hot tables | Per-input resolved-reference arrays; reduce hot name/version lookups and record allocation | Byte identity against 1.0 where policy is unchanged; targeted TLS/IFUNC/version/weak/COMDAT tests; fewer allocations/cache misses or lower CPU |
| Deferred: controlled parallel work | Outside the active track; revisit only after agreement to resume parallel work | Preserve the ordered resolution, diagnostics and isolation requirements discussed above |
| P4: measured secondary costs | GC graph, merging, layout, hashing or output I/O according to the new profiles | A measured workload bottleneck and a gain that survives end-to-end comparisons |

P0 can reorder P1/P2 if current profiles disagree. These are experiments with
keep/revert criteria, not a schedule or a claim that every proposed optimization
will win. A daemon, persistent cache or incremental patcher is a later product
decision after fast full linking is established. No LTO, C++ scope expansion,
runtime dependence on either reference linker, or third-party package is needed
for this initial track.

For P0, extend the existing replay tools rather than invent a second harness:

- Include tiny native Fas links, Sieve, SQLite, Chibicc dynamic/static, a shared
  library pair, and available larger qualified C inputs such as curl/Redis.
  Add sparse/dense archive extraction, thin/mixed partial pipelines, many sections,
  debug-heavy input, GC and static PIE as distinct cases. Respect 1.0 input limits;
  the multi-GiB applications in mold's charts are outside our current contract.
- Reuse exact precompiled objects for all tools. Record scripts, libraries,
  sysroot and transitive dependencies as well as explicit argv files. Report an
  unsupported competitor configuration instead of silently changing flags.
- Measure external wall time through exit, CPU, peak memory, output size and
  raw samples. Time compilation and runtime validation separately. Use rotated
  orders, warm-ups, repeated trials and a quiet-PC interval for comparisons.
  Preserve the historical reports; do not relabel them as 1.0 results.
- Separate default-worker comparisons from controlled worker-count scaling.
  Account for physical cores/SMT and shared-PC load. For mold disable its fork
  latency-hiding path for full-process comparisons; otherwise observe the entire
  process tree and label caller-visible latency separately. Label output reuse
  versus fresh output explicitly. A one-process RSS sample is not process-tree
  memory, and shared mapped pages complicate summing RSS across processes.
- Keep timings without `--stats` or profiling enabled. Add exclusive nested-pass
  timing or document inclusive spans clearly. Current `Stats` allocation counters
  describe one domain and will need worker-local aggregation before multicore
  comparisons. Keep worker failures bounded, joined and deterministic.
- For each implementation change, compare Fas before/after bytes, maps and
  repeatability where behavior is intended to stay fixed. Competitor ELF images
  need matching runtime/structural behavior, not cross-linker byte identity.
  Run relevant existing regressions, then the complete acceptance suite for the
  combined candidate. Extend tests only for new behavioral/concurrency risks.

The first concrete next action is **P0 profiling of the released source**, with
archive-index/string allocation as the leading hypothesis. A 2x-over-LLD target
remains an aspiration to test against named workloads, not a forecast established
by reading another linker's benchmark table.
